## Principles & Gotchas to Carry Forward

- **The Supabase MCP connector can be authorized against the wrong account/org silently** — it will work (list projects, etc.) but simply won't see the project you need. If `get_project` on a known ref returns a permission error, or `list_projects` shows unfamiliar projects, the fix is: user goes to claude.ai → Settings → Connectors → Supabase → disconnect → reconnect, choosing the correct account/org at the OAuth screen.
- **Migration files that create RLS policies must respect table-creation order for cross-table policy references.** `001_initial_schema.sql` as originally written violates this once (`leagues_member_read` references `league_members` before it exists). Check for other cases before assuming any migration file in this repo is safe to run as-is.
- **Migration 002 (seed data) is idempotent and self-contained** (uses `ON CONFLICT DO NOTHING` throughout, wrapped in a single `DO $$ ... $$` block) — should be safe to run later without needing the same scrutiny as 001, but it has not actually been tested this session.
- **Two separate email systems — do not conflate them (repeated from prior brief, now confirmed as an active blocker):** the app's `RESEND_API_KEY` sends the app's own emails (invites, on-clock, standings). The magic-link login email is sent by **Supabase Auth's own email provider**, controlled separately in Supabase Dashboard → Authentication → Emails, and is rate-limited (~2/hour) on the default `noreply@mail.app.supabase.io` sender. This limit was hit during this session's debugging and blocks further magic-link testing until it resets or SMTP is switched to Resend.
- **PKCE-based magic-link exchange (`exchangeCodeForSession`) depends on a `code_verifier` cookie set in the browser that originated the `signInWithOtp` request.** If the link is opened in a different browser/app (e.g., a mail app's embedded browser vs. Safari), that cookie won't be present and the exchange fails **silently and client-side** — no request to Supabase's `/token` endpoint is even made. This is invisible from Supabase's side (their logs show a clean, successful `/verify`) and can only be diagnosed by noticing the *absence* of a subsequent `/token` call in the auth logs. The robust fix is Supabase's `token_hash` + `verifyOtp()` pattern, which has no cookie dependency.
- **Magic links are single-use.** A second click on an already-consumed link correctly produces `otp_expired` / "Email link is invalid or has expired" — don't mistake this for the primary bug if it shows up in testing; check the auth log timestamps to see if an earlier click on the *same* link already succeeded at the Supabase level.
- **`mcp__Supabase__get_logs` (service=`auth`) is the fastest way to distinguish "Supabase-side failure" from "app-side failure"** — look for `/otp` (email requested), `mail.send`, `/verify` (link clicked, redirects to app callback), and critically `/token` (app exchanging code for session — its absence is the smoking gun for the callback bug).
- **Several MCP tool calls this session (migration applies, and even an `AskUserQuestion` call) came back as "rejected by user" during a period when the Supabase/GitHub MCP connections were visibly flapping (disconnect/reconnect messages in the system reminders).** It was never fully confirmed whether these were genuine user rejections or an artifact of the reconnect cycle — worth asking the user directly if this recurs, rather than assuming intent.
- **Supabase's SQL Editor "Potential issue detected" destructive-operation warning is a blunt keyword scanner** — it fires on any `DROP`/`DELETE` keyword regardless of context (e.g., a guarded `DROP CONSTRAINT ... ADD CONSTRAINT` in the same statement, or a `DELETE` inside a conditionally-skipped `DO` block). Read the actual SQL before reassuring the user it's safe — don't dismiss the warning reflexively, but don't be alarmed by it either.

- **GitHub access is via `mcp__github__*` tools only** (no `gh` CLI), scoped to `mrkfrnzn/zenithailabs`. Default branch `main`.
- **This session's designated working branch is `claude/cfp-war-chest-login-130i89`** (per harness instructions), currently a zero-commit fork of `main`. The prior session's branch `claude/cfb-futures-mvp-ju2Cw` (with `scripts/setup-database.sql`) still exists separately and was never merged.
